# R1 — Application runtime integration

## Scope
Connect runtime DB access, Next.js ingestion command/API to canonical acquisition, durable job dispatch/state, and worker handoff.

## Status
Durable staging implementation is present on PR #25 branch. Canonical content, source, acquisition runs, processing, transcript, and video-frame rows persist in Postgres; artifact files persist under configured `CIC_STORAGE_ROOT`; one worker claims jobs with DB lease and recovers interrupted `RUNNING` jobs.

## Acceptance
- Next.js route invokes canonical acquisition boundary, not provider-specific logic. **PASS** — `/api/processing` enqueues through `createDefaultAcquirer` and `createPostgresRuntimeFromEnv`.
- Runtime DB connection uses canonical schema and truthful errors. **PASS in disposable Postgres staging** — `CIC_DATABASE_URL` plus workspace/brand/batch IDs are required; DB failures return error responses.
- Acquisition and processing state survive restart/reload. **PASS** — Postgres rows and configured storage artifacts reloaded by a new runtime instance.
- Worker handoff is durable without Redis/Kafka/microservices. **PASS in staging** — `scripts/worker.mjs` uses atomic `FOR UPDATE SKIP LOCKED` claim; `recover()` requeues interrupted jobs.
- Duplicate URL is idempotent. **PASS** — unique workspace/content job and canonical content identity; completed enqueue returns existing completed result.
- Fixture-only route is replaced or explicitly isolated from runtime path. **PASS** — home/API use durable runtime.

## Verification
Disposable Postgres actual-media flow: public TikTok URL → DB job → worker claim/recovery → yt-dlp → ffprobe/ffmpeg/faster-whisper → persistent artifacts → canonical rows → UI-shaped public artifact URLs. Completed result: 56 frames, 23 transcript segments, one canonical content row, one job. Interrupted worker proof: pre-claimed job recovered by new worker and completed with `attempt_count=2`; no duplicate content; 56 frames upserted.

## Limits
AWT remains unavailable/not implemented. Staging smoke uses disposable local Postgres and `/tmp/cic-r1-storage-final`; deployment must provide real persistent volume/database configuration. No S5 ranking engine.
